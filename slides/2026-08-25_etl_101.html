There is no “right” way to build things

A pipeline that runs once a year and one that runs once a second are both ETL, but they should look nothing alike.

Most arguments about which ETL tool or pattern is “right” are really trade-offs around which constraints matter most.

Once you know define those constraints very precisely, most of the design questions get easier to answer.

This is the through-line: what shape a pipeline should take depends on what you’re constrained by. If someone asks “is Airflow better than dbt?” or “should we use Dagster?”, the honest answer is almost always “for what cadence, at what stakes?”

Different design considerations

Some examples:

Once a year Monthly Weekly Nightly Hourly Real-time
Regulatory filing Utility bill Gas price update Satellite imagery processing Weather forecast Smart-meter / grid telemetry


  • The right pipeline for a yearly filing looks nothing like one for live telemetry
  • No pattern is “better” in general, constraints like cadence and stakes might tell you which one fits
  • Other constraints also contribute, liken: compute cost, data volume, team size, data sensitivity, data lineage requirements etc.

So what actually is ETL?

Moving data from its source to where it can be useful (and reshaping it along the way).

  • Extract: pull it out of the source system.
  • Transform: reshape it into some form that’s useful to downstream users or systems.
  • Load: put it where it can be easily accessed.

Keep the definition to one sentence. Every added qualifier now costs clarity later.

Data warehouses and lakes get defined properly in the Database Design session. For today: “a place optimized for reading and analysis, rather than for running an app.”

Why does ETL exist at all?

Two main reasons:

  • Raw data is rarely shaped “right”. The source system was designed for its job, not your use-case.
  • You probably don’t want to hit the source every time. Partner APIs have rate limits, files get moved, data can disappear, schemas drift, etc.

Source systems are optimized for serving an app or processing a transaction, not for being queried by ten other teams.

A running example

A partner exposes emissions data in an API; we want it summarized in a dashboard.

  • Extract: authenticate to the partner API, page through results, handle their rate limit.
  • Transform: normalize units (they report in kilotonnes, we standardize on tonnes), map their facility IDs to ours, drop test records, validate that no value is negative.
  • Load: upsert into emissions_by_facility, keyed on facility + reporting period.

The example is deliberately banal so nobody gets distracted by the domain. The point is the shape. Walk it once, naming each stage. The kilotonnes/tonnes conversion reappears in the schema-on-read failure mode; plant it here so the payoff lands.

Note: ETL vs. ELT

Mostly a question of where you put your compute, and how much raw history you keep.

Order Where transform happens Choose when…
ETL E → T → L In a separate processing layer, before landing in the destination • destination compute is expensive or limited
• sensitive data must be scrubbed before it lands
• storing raw is undesirable
ELT E → L → T Inside the destination, using its own compute • destination compute is cheap and elastic
• you want to keep raw so you can re-derive when logic changes
• multiple consumers need different views of the same source

ELT got popular when cloud warehouses (Snowflake, Databricks) made it cheap to load everything raw and transform later in SQL. For today: I’ll say “ETL” and mean “either.”

The underrated ELT advantage: you kept the raw data, so you can re-derive everything when the business logic changes. The same is possible under ETL, but more cumbersome: you may have to re-ask a partner for history they no longer have.

Don’t over-index. Most of the room won’t remember the distinction in a week, and that’s fine. The point of naming ELT is so nobody thinks I don’t know it exists.

Anatomy: Extract

Pull data out of the source.

  • Pull vs push: does your pipeline reach out and grab data (poll an API, query a DB), or does the source push at you (webhooks, event streams)?
  • Full vs incremental: pull the entire dataset every time, or only what changed?
  • Source constraints: rate limits, replica lag, lock contention on production DBs, pagination quirks, schema drift you don’t control.
df = pd.read_json("https://api.partner.com/v1/emissions")

Planting this forward reference is what makes the CDC slide land later. Do not skip it.

Anatomy: Transform

Reshape the raw pull into what downstream users actually want.

  • Data cleaning: nulls, encoding issues, malformed records, deduplication.
  • Transforming and casting: type coercion, parsing, reshaping fields.
  • Joining and merging: combining rows or columns across sources.
  • Aggregation: grouping and summarizing (sum, mean, count, rolling windows).
  • Filtering and sorting: keeping only the rows you need, in the order you need them.
  • Data enrichment: adding derived columns or joining reference data (e.g. facility metadata).
  • Normalization: standardizing units, time-zones, currencies, naming across sources.
  • Validation: enforcing business constraints; reject or quarantine bad rows rather than silently loading them.
df.groupby(["facility_id", "year"])["scope_1_tCO2e"].sum()

These aren’t a strict order; most pipelines interleave them. Validation is the one people skip. Reject or quarantine beats silently loading garbage.

Anatomy: Load

Put the reshaped data where downstream users (could be you) can read it.

  • Full load / overwrite: replace the destination table wholesale. Fits when consumers only ever want the current snapshot.
  • Append: add new rows only. Fits when consumers query events over time and treat each row as immutable.
  • Upsert / merge: insert new, update changed, based on a key. Fits when consumers want “current state per key” and don’t need change history.
df.to_sql("emissions_by_facility", conn, if_exists="append", index=False)

This is a common source of friction between pipeline owners and pipeline consumers, and it’s usually decided backwards, by whatever was easiest to write.

Idempotency

A pipeline run is idempotent if running it again with the same input produces the same result: no duplicated rows, no double-counted totals. It matters any time you might have to retry or backfill.

Symptom: “The job failed halfway through, so I re-ran it, and now this facility’s emissions are counted twice.”

That’s: a non-idempotent pipeline. One of the most common reasons numbers stop reconciling across runs.

Maps to the requirement: if a human or a scheduler might ever re-run this, it must be safe to re-run. Usually achieved by upserting on a stable key, or writing to a fresh partition and swapping it in atomically.

Idempotency is one of the words you most want people to walk out remembering. It comes back in every later topic (Jobs & Queues, API design, CI/CD).

Pair this with the next slide deliberately: idempotency and backfill are the same problem from two directions. That pairing is what makes idempotency feel urgent rather than academic.

Backfill

Re-running a pipeline over historical data, e.g. because of a bug fix, a change in schema, or a changed business rule.

Symptom: “We found and fixed the bad emissions factor calculation last week, but last year’s dashboard numbers are still wrong.”

That’s: a fix that was never backfilled, or a pipeline that we don’t trust enough to backfill.

Maps to the requirement: fixing forward is only half a fix. Non-idempotent pipelines make backfills dangerous, which means they don’t happen, which means historical data quietly stays wrong.

Ask the room: has anyone here actually tested a backfill on a pipeline we own? The honest answer is usually no. That silence is the point.

Batch vs Streaming (vs Micro-batch)

  • Batch: processed in discrete chunks on a schedule (hourly, nightly). Simple, easy to reason about, higher latency.
  • Streaming: processed continuously as it arrives. Lower latency, meaningfully more operational complexity.
  • Micro-batch: the practical middle ground: small batches every 1–5 min. Usually what “real-time” actually means in production.

Symptom: “Stakeholders keep saying the dashboard is out of date, but the pipeline runs fine every night.”

That’s: the pipeline doing exactly what it was told to do. The consumer expected fresher data than a nightly run gives them. Start with that conversation before you change the schedule.

Point back at the spectrum slide here. This is the vocabulary for the picture I put up in the cold open; gesture at it if it’s still visible.

Assume “ETL” means “batch pipeline” unless someone says otherwise; we’re probably not building Twitter. Streaming comes back in Jobs & Queues where the event-driven model is central.

Orchestration

The system responsible for scheduling pipeline steps, managing dependencies, retrying failures, and alerting (Airflow, Dagster, Prefect, cloud-native schedulers). Distinct from the transformation logic itself.

Symptom: “The pipeline didn’t run last week because Sam was on leave.” Or: “Step B started before step A finished, because we guessed at the cron times.”

That’s: missing orchestration. Whatever’s currently scheduling the run — someone’s calendar, a cron on a laptop, a person remembering — is doing the job of an orchestrator, badly.

Maps to the requirement: this is the direct answer to “what’s stopping you from scheduling it?”, and the bridge into Jobs & Queues (topic 2), where retries and dependencies get treated properly.

DAG = Directed Acyclic Graph. Don’t unpack the acronym unless someone asks. The point: “there is a thing that decides run order and handles failure, and it has a name.”

Data quality / observability

Monitoring for freshness (did it arrive on time?), volume (did row counts change unexpectedly?), schema (did a column vanish or change type?), and distribution (did values suddenly shift?).

Symptom: “The partner API returned an empty response for three weeks. The job reported success every night. We found out when someone noticed the chart was flat.”

That’s: a pipeline with no observability. The scary part is that the job succeeded every night — a green run doesn’t tell you the data is right.

Maps to the requirement: a pipeline that can fail silently will fail silently. The cheapest useful check is a row-count sanity bound; it catches a surprising share of real incidents.

This failure mode hits hard at RMI-style orgs because our outputs feed decisions and reports rather than user-facing product surfaces — bad data can sit in a report for months without anyone noticing.

The moment to land is that the job succeeded and the data was still wrong.

Latency vs Throughput

  • Latency: time from an event happening to it being available downstream.
  • Throughput: volume of data processed per unit time.

Symptom: “We batched the API calls to handle more records per run, and now each record takes twice as long to appear.”

That’s: the latency/throughput trade-off. Optimizing hard for one routinely costs the other.

Maps to the requirement: know which one your consumer actually cares about before optimizing. Returned to properly in Session 2.

Short slide: the trade-off gets its full treatment next session. The useful move here is just making people notice these are two different things that get conflated.

Partitioning

Splitting data (usually by date) into separate physical chunks so queries and reprocessing can target a subset instead of scanning everything.

Symptom: “One year of data was bad, and fixing it meant reprocessing all twenty years.”

That’s: an unpartitioned dataset. Partitioning lets you reprocess just the affected slice instead of the whole table.

Maps to the requirement: partition on the dimension you’ll most often need to reprocess by: usually time, and usually not the dimension you’d pick for query performance alone.

Tie back to backfill explicitly: partitioning is the thing that makes that problem survivable.

Schema-on-write vs Schema-on-read

  • Schema-on-write: structure enforced at load time (traditional DBs, structured warehouses).
  • Schema-on-read: structure interpreted at query time; storage just holds raw or semi-structured data (lakes, object storage).

Symptom (schema-on-write): “The partner added a column and the whole job crashed.”

Symptom (schema-on-read): “The partner switched their units from kilotonnes to megatonnes. Nothing crashed. The numbers were just wrong for six months.”

That’s: the real trade-off between the two: loud failures vs. silent ones. Schema-on-write means you’ll deal with the pipeline breaking whenever a source changes. Schema-on-read means it keeps running, and you might not notice the numbers are wrong until someone spots it downstream.

This is the payoff for the unit conversion we planted in the running example. Call that back explicitly.

Both failure modes are real; you’re picking which kind of pain you’d rather have.

Slowly Changing Dimensions (SCD)

Pattern for handling attribute values that change over time.

  • Type 1: overwrite, no history kept.
  • Type 2: new row per change with validity date ranges, full history.
  • Type 3: limited history via extra columns (e.g. “previous value”).

Symptom: “That plant changed ownership in 2022. We updated the owner field, and now every tonne it has ever emitted is attributed to the new owner.”

That’s: a Type 1 overwrite where the analysis needed Type 2.

Maps to the requirement: ask “will anyone ever need to know what this value was at a point in time?” If yes, you need Type 2. You can’t reconstruct history you never stored.

Domain-relevant and memorable. Push the point that you can’t recover history you never stored — that’s what gets people to plan for Type 2 upfront.

Change Data Capture (CDC)

Detecting and extracting only rows that changed since last read, typically by reading the source database’s transaction/replication log rather than re-querying the table. It’s how most near-real-time pipelines pull from OLTP databases.

Symptom: “A record was deleted at the source months ago. It’s still sitting in our warehouse.”

That’s: timestamp-based incremental extraction, which can’t see deletes: a row that’s gone has no updated_at to find. Missing deletes is what usually pushes a team to adopt CDC.

Close the loop: this is the forward reference flagged back in the Extract section. Call back to it explicitly so the plant pays off.

Data lineage

The traceable path of data from source to destination: which pipeline produced this table, from which upstream sources, via which transformations.

Symptom: “Someone renamed a column upstream. We found out which dashboards depended on it when their owners started complaining.”

That’s: missing lineage. You don’t feel the gap when you’re building the pipeline — you feel it every time someone asks “what will break if I change this?”

Maps to the requirement: lineage is what makes impact analysis possible: “if I change this, what breaks?” Returns in the capstone.

The build-vs-change distinction is the useful bit here: lineage costs nothing when you’re writing the pipeline and everything when you’re modifying it a year later.

The one thing to remember

The shape of your pipeline should follow from your constraints, not from copying the fanciest team’s setup.

No single tool or pattern wins in general. What actually decides it is frequency (how often does it run?) and stakes (how bad is it if it’s wrong or late?).
